# Content Kanban

The board is an opt-in post-type capability: `->kanban()` or `apply(['kanban' => true])`. Only Jobic's built-in `post` registration enables it; `page` and other types remain disabled. Disabling it removes the list toolbar link and makes direct board endpoints return 404. The board uses the shared Domi document in full-screen mode, with Back and an in-page settings dialog.

## HTTP and access

- `GET /admin/posts/{type}/kanban` renders the full-screen page.
- `GET .../kanban/data` returns the active definition and first page of each column. Optional `state`, `cursor`, and `definition_id` request another page of just one column.
- `GET .../kanban/{post}` returns authorized card details, safe rendered editor content, optional embedded editor URL and current transition previews. Optional `locale` is restricted to installed active languages.
- `POST .../kanban/command` accepts `settings`, `move`, or `reorder`. Settings accepts `page_size` in 5, 10, 20, 50. Movements carry post, definition, revision and stream version, target state, column version, and optional `before_id`. Cross-state moves also carry transition and source column version. Scheduling accepts `due_local` in the active language calendar or an ISO `due_at`.

All reads require the registered type view permission. State roles additionally filter cards and counts. Restricted columns expose state metadata but no cards, counts or cursors; authorized transitions to them remain possible and remove the moved card from the current user's view. Commands repeat access decisions under the type/owner/stream lock order. Movements require the registered workflow manage permission. Settings requires only view access. Unauthorized HTML renders the shared in-shell 403; JSON returns 403.

## Pagination and ordering

Page size is stored under `users.ui_preferences.kanban.{type}.page_size`, defaults to 5, and is independent per user and type. Settings updates lock the user row and preserve unrelated preferences. Columns have independent encrypted cursors bound to actor, type, state, active definition and column ordering version. Every query uses stable rank/ID ordering and reads at most page size plus one.

Shared ordering lives in `post_kanban_columns` and `post_kanban_positions`, each owned by one new migration. Rank allocation queries immediate neighbors and rebalances a column only when a gap is exhausted. Type-level workflow locking serializes reorders and cross-column moves. State changes through other entry points append a new target rank and invalidate both affected column cursors, including columns never previously reordered. Unranked newly created cards use a stable ID-based rank. Old cursors/versions return 409; the board refreshes data and offers retry. Foreign edit leases return 423. Post editor documents, including embedded forms, use distinct tokens under the same owner lease. They await their own release before switching locale and suppress duplicate unload releases; closing one document cannot release another document’s token. Transient board commands retain the existing primary lease rather than releasing document-owned holders. Transient board-owned leases are released even after failure.

## Conditions and legacy definitions

`laravel-post` 1.3.1 provides direct transition `roles`, the shared `WorkflowTransitionAccess`, and `WorkflowTransitionPreview`. Role restrictions are enforced before running actions. The old role task is hidden from Jobic's library; one unambiguous active role task converts to direct roles when a graph is read/validated. Multiple or permission-key tasks remain enforced and carry an inspector warning; administrators review and remove them explicitly rather than silently changing their meaning.

Previews inspect the immutable revision used by actual execution. Built-in validation/restriction tasks run only their read-only checks. Actions are never invoked. Unknown custom conditions are not instantiated in previews and return `unknown`, which the board shows in amber and permits users to attempt. Custom conditions may implement `WorkflowConditionPreview` for safe previews. All conditions are repeated on actual drop under stream version locking.

## Embedded editor and accessibility

The board reuses `posts.form` with the common embedded layout via `?embedded=kanban`, preserving the existing editor, media, taxonomies, translation fields, history, version checks and edit lease renewal. The parent document stays mounted. Locale changes and closing ask the embedded unsaved guard before discarding edits. The shared embedded form hides its duplicate transition controls; the popup footer uses the board transition commands after confirming unsaved changes and releasing only its owned lease. Ordinary saves refresh cards and popup destinations while keeping the embedded form mounted. Cross-origin framing remains disallowed by the existing security headers.

The same-origin embedded editor exposes only a `canClose()` guard and emits local `jobic:kanban:saved` / `jobic:kanban:changed` DOM events with no payload. These refresh already-authorized board reads and never grant access. Read-only users receive server-rendered sanitized editor content and no editor URL. Move controls provide keyboard/touch alternatives to desktop drag and drop; the insertion marker follows visible card geometry, ignores the dragged card and does not change when its position is unchanged; dialogs use the browser's focus trap, Escape handling and focus restoration. Visible dates use LocalizedDate; scheduling input roundtrips the active calendar and locale digits on the server.

## Planning, calendar and insights

A card may have one assignee, an editorial deadline and up to 20 dependency links. These live in Jobic-owned `kanban_card_meta` and `kanban_card_dependencies` tables, each with one owning migration. Assignment is distinct from the first revision's author. The assignee must be an active board member with the content type's view permission and access to the card's current workflow state. Dependencies must refer to visible cards on the same board and may not create cycles. The deadline picker uses the site's Domi datetimepicker in the active language's calendar, with visible month and year selectors in the board dialog. `KanbanCardMeta::dueLocal` converts the calendar-aware form value to a UTC `Y-m-d H:i:s` database timestamp and formats it back in the administration timezone using the active language record through `CalendarInput` and `LocalizedDate`. Dependency search results show the title, ID and current state. Card work saves require workflow management permission, a matching metadata version, board configuration version, and a compatible edit lease. The service rechecks access under the workflow lock, writes both tables in one transaction, and broadcasts an empty type-level invalidation after commit. No card data is included in Reverb events.

The board's **My work** control filters columns and counts by the authenticated assignee. The member directory also lets a viewer filter by a chosen assignee; its separate card count describes authored cards. These temporary filters do not change shared card rank. Personal page size remains independent for each user and board.

The calendar endpoint returns one month in the active language record's calendar, including day labels generated through `LocalizedDate`. Pending publication actions and editorial deadlines become separate event types. Month offsets are bounded to one year, and event output is bounded to 500 cards per visible state with a truncation indicator. The workflow insights endpoint reports visible card count, average days in state and stalled count per visible state. Both endpoints use the same board filters, current search, quick filter, My work selection and state-role visibility as column reads. They expose no counts for restricted states. Every route uses the registered post-type view permission, custom-board audience and board version checks.

The header contains compact controls for My work, calendar and insights. Personal saved views and their command have been removed; existing preference data is left untouched. Details keep card work in a collapsible section beneath the embedded editor. Its fields use the board's panel palette and icons. Cards align author and assignee in one row; the fixed-corner selection checkbox appears on hover or keyboard focus and remains visible while selected. Touch devices keep it visible. The publication calendar returns the server's current date for its today marker and offers calendar and date-sorted table views. Month navigation and view switching live in the shared dialog `header-actions` slot; deadlines and publication actions use distinct icons and colors; insights show a visible-card total, per-state proportions and detailed metrics. The existing calendar-aware date parser accepts editorial deadlines; `LocalizedDate` renders stored dates, and cards distinguish overdue and next-day deadlines. Publication, including scheduled execution, is rejected while any linked prerequisite remains unpublished. The modal retains the existing unsaved-change guard and focus behavior. The view shell and toast are shared with the workflow editor. Extension hooks for card-work saves are documented in `docs/hooks.md`.

## Workspace presentation and native dragging

Kanban and the workflow designer use the same `WorkflowPageHeader`, `WorkflowSettingsDialog`, `WorkflowToast` components and `workflow-shell.css`. The shared settings dialog preserves native focus trapping and uses the designer's existing header, icon, panel and button presentation. Board cards have explicit document, drag-grip and labeled move affordances; their layout is maintained in `resources/css/kanban.css`.

Every descendant of a column participates in native dragover, including empty messages and column headers. A drop retains its drag session while awaiting condition previews or a page needed to locate the insertion point. An existing in-flight column-page request is reused rather than canceling the drop or fetching twice. Native dragend clears only an abandoned drag, never a drop currently being processed. Browser regressions exercise actual mouse dragging, delayed previews, delayed and already-in-flight pagination, plus exact computed-style parity with the designer's header, settings dialog and toast.

## Simple and managed boards (Post 1.4.0)

`kanban()` enables the existing default board. `multipleKanban()` enables both Kanban and the board directory; `hasMultipleKanban()` reads it. `multipleKanban(false)` preserves the simple board, while `kanban(false)` disables both. Chain calls apply in order. Array configuration supports boolean `kanban` and `multiple_kanban`; true multiple implies true Kanban regardless of key order. Only `post` opts into multiple boards. Disabling either capability never deletes stored data.

The existing `/kanban` URL opens the directory in multiple mode and the simple board otherwise. `/kanban/default` always opens the legacy board. `/kanban/boards/{board}` is the custom workspace; its `/data`, `/posts/{post}` and `/command` endpoints repeat capability and audience checks. Directory `/boards/data` is audience-filtered, `/boards/manage` requires independent `{type_manage_permission}.kanban` (for posts, `admin.content.posts.manage.kanban`). Creating, PUT updating and DELETE removing `/boards[/{board}]` require that same registered permission and base content visibility. Management does not override a board audience. Role membership (including parents) OR direct user selection admits the viewer; both empty means no additional board restriction. Existing state restrictions and workflow movement permission remain mandatory.

Custom definitions, columns and positions have separate owning migrations. Legacy rank tables and preferences remain unchanged for the default board. Custom preferences use `ui_preferences.kanban.{type}:board:{id}.page_size`. Shared post state propagates to all boards, but ranks and ordering versions are isolated. A deletion cascades only custom layout data. Workflow and board locks serialize definition edits and moves. Custom commands and detail reads carry `board_version`; cursors bind actor, board, configuration version, workflow and column version. Initial reads may omit board_version to refresh changed settings without reloading the document. Removed states fail with a translated configuration error; they are not automatically substituted.

### Filter drivers

Register trusted instances through `app(KanbanFilterRegistry::class)->register('stable_key', $driver)` during application boot. Keys are unique; drivers implement `App\Contracts\KanbanFilterDriver`. `supports(type)` must be cheap; `form(type)` returns a translated label and declarative select `fields` (key, label, options `{id,name}`, optional multiple; dependent selects may declare dependsOn and optionsBy). `validate(type, config)` validates and normalizes all input; `apply(EloquentBuilder, config)` only adds restrictions and must not write, dispatch actions or execute the query. Browser configuration never contains executable code. The built-ins are `author` (first shared revision creator) and repeatable `taxonomy` (enabled collection and matching term IDs). Drivers combine with AND; selected IDs combine with OR. Unknown drivers, invalid collections or missing terms fail closed, including on stored board reads. Invalid settings never expand the audience.

The management form uses shared field components, Select2, AJAX transport, pending buttons, inline errors, unsaved guards and CRUD dialogs. Custom extension views may use `jobic.admin.posts.kanban.boards.before/after` with type context. Core default-board workspace slots remain available. Saving remains in the same document; Save and new/close are explicit in-document intents.


### Management directory and audit

The directory uses the Domi DataTable only on this page, bounded server queries, allowlisted name/date sorting, search, external pagination and Select2 page length. Audience statistics are scoped to the current accessible or explicitly authorized management listing. Selection persists across paging/filtering in this document and is reviewed through the shared CRUD dialog. `POST /kanban/boards/bulk` accepts at most 100 explicit `{id, version}` items and deletes atomically; one missing/stale item rolls back the entire selection. The default board cannot be selected for deletion. `GET /kanban/boards/{board}/history?page=N` requires management permission and returns 20 shared RecordHistory entries per page. History records only name, audience identifiers, state selection and normalized non-secret filters inside the same transaction; filter configuration must never contain credentials or tokens. Board forms reuse the shared before/after history renderer and explicit Save / Save and new / Save and close controls.

Deployment on this development site applied the three additive `2026_11_10_*content_board*` migrations without clearing existing tables. The package remains a stable Composer dependency; no local path overrides are required. Browser fixtures cover both modes, real mouse dragging, custom workspace preference versions, managed forms in both languages and viewport sizes, field errors, unsaved cancellation and versioned selection across pages.


### Independent board management pages

The directory has one view: managers see all definitions and management actions, while viewers see only their allowed boards. A manager still cannot open cards from a board outside their audience. The former management-mode toggle is removed; the legacy management JSON endpoint remains authorized for compatibility. Add opens `GET /kanban/boards/create`, Edit opens `GET /kanban/boards/{board}/edit`; both require board management permission at the route boundary. These pages use the Roles form's tabs, sticky header and Cancel + split Save structure. Ordinary Save remains in the document, updates the edit URL with history.replaceState after creation, and retains optimistic version checks; explicit Save and new / Save and close navigate after successful persistence. Directory Back uses the Taxonomy list's title back link, and Default board remains in the top toolbar. Board management and workflow settings live inside the content list Actions menu; the default Kanban board is a separate toolbar button between Add and Actions.


### Board form controls

Details and audience share one tab; the remaining tabs are Columns and Filters. Columns use two accessible lists instead of a select: available states are added once; selected states use icon-only up/down/remove controls with translated names, tooltips and focus restoration. Removing a selected state returns it to the available list and never changes the workflow. The serialized ordered `states` payload is unchanged. Filter cards retain driver-based validation and shared Select2 controls, with labeled types/fields, translated hints, an empty state and icon removal. Directory guidance lives in the Help dialog rather than beneath its title. Content-list Actions group Delete, then Manage Kanban boards (only for multiple-board types) and Workflow settings (when authorized), then Help and Release edit locks, with separators only between nonempty groups. The default Kanban board is a separate toolbar button between Add and Actions. Live presentation changes rebuild these controls from the current translated registry, including navigation and bulk-action labels. Directory statistic icons represent all boards, open audience, restricted audience and recent creation with Kanban, globe, shield and calendar respectively.


### Directory and editor refinements

Row actions show an icon link to Open the board outside the menu; Edit and Delete remain inside it. History is a shared paginated panel on the board form, including after the first successful creation, and is not exposed as a list popup. Name takes the largest table column; date and icon actions have narrower bounded widths. Live locale updates explicitly refresh DataTable header labels and row actions. Bulk Delete in post and taxonomy toolbars appears only while a selection exists. Post Actions suppress the shared Help top border because their explicit group separator already supplies that line.

Each post editor document now has an independent holder token beneath its owner’s cache lease. Delayed unload beacons remove only that token; owner reuse, foreign-user exclusion, expiry, administrative release and optimistic content versions remain enforced. Sibling tokens never appear in returned lock metadata. Presentation-only AJAX GETs reuse an existing lease rather than create a new document holder. The post unsaved guard compares editor blocks without transient Editor.js time/version/generated IDs; real content changes and meaningful blank paragraphs remain protected.


### Board directory filters

The shared filter drawer filters board definitions, not their content cards: audience kind (open/restricted), presence of stored content filters, selected workflow states, and configured roles/users. Roles and users are management-only filter fields; direct queries for these fields by viewers return 403. Each multi-select uses OR internally, while different filter fields and text search combine with AND after the audience scope. Filters are validated, applied in SQL before filtered counts and pagination, retained during sorting/paging and cleared by Reset. Summary tiles remain unfiltered within the authorized directory scope, matching the shared CRUD statistics contract. Selection survives filtering in the current document; no preferences or board settings are written by filter reads.

## Workspace tools

The fullscreen workspace reuses the workflow header, settings dialog, shared toast and existing Kanban palette. Title/ID search and temporary author/taxonomy driver filters combine with the board's fixed restrictions. Summary counts (visible, scheduled, waiting beyond the configured threshold) exclude role-restricted states and use the same fixed and temporary filters. Selecting a summary filters cards without changing the overview totals. These temporary restrictions do not change board membership, transition authorization or shared order.

Personal preferences now include `density` (`full`/`compact`), `card_fields` (`image`, `terms`, `author`, `updated`, `age`, `assignee`, `scheduled`, `deadline`, `dependencies`) and `group_by` (`none`, `author`, or `taxonomy:{collection}`), under the existing per-user/per-board key. Existing preferences gain the four new fields by default until saved with `card_fields_version=2`; thereafter the saved selection is exact. Core card identity, selection and move controls remain visible. Cards use the author's actual `User::avatarUrl()` with initials fallback. Human-facing dates still use `LocalizedDate`; age is time since the latest actual state change, including workflow migrations and excluding self-transitions. Grouping by taxonomy assigns a multi-term card to its lowest-ID term in the collection, so it never duplicates cards. Unassigned cards have their own lane. Lane lists load 20 at a time; each lane/state cell retains independent five-card cursor loading. Dragging changes state within the current lane; changing author/terms uses the existing content editor.

`kanban_workspace_options` owns versioned shared `stale_days` and per-state `{state, limit, mode}` capacities. Its single owning migration is additive and requires no reset. Zero capacity means unlimited; `warn` decorates the column counter, while `enforce` also rejects state changes at the shared stream persistence boundary, including ordinary forms and scheduled execution. Workflow locks serialize transitions and capacity saves. Each applicable board's fixed filters determine its capacity membership, independently of temporary filters and user visibility; failure messages do not reveal another board's name or counts. Disabled Kanban capabilities preserve options while suspending their associated capacities. Deleting a custom board cascades its options. Configuration version conflicts return 409.

Selection supports at most 50 cards. The bulk dialog reads each card's authorized destinations, asks for a transition per card and a calendar-aware time when needed, and submits operation `bulk` with `items`. The server rechecks revision, stream/column/configuration versions, edit leases, roles and transition conditions for each item. Individual savepoints preserve successful items while reporting failures separately; failed cards remain selected. Bulk execution uses the existing workflow-management permission.

## Laravel Reverb

Install dependencies with Composer and npm as usual; the repository includes `laravel/reverb`, `laravel-echo` and `pusher-js`. Configure `BROADCAST_CONNECTION=reverb`, a unique `REVERB_APP_ID`, public `REVERB_APP_KEY`, private `REVERB_APP_SECRET`, and the internal `REVERB_HOST/PORT/SCHEME`. `REVERB_PUBLIC_HOST/PORT/SCHEME` identify the browser endpoint; only those public settings and the public app key enter Domi. Restrict `REVERB_ALLOWED_ORIGINS` to application hostnames. Never commit real app credentials.

Run `php artisan reverb:start` as a supervised long-running process alongside the web application. Production normally proxies secure WebSockets to Reverb; restart the process after configuration changes (`php artisan reverb:restart`). Direct TLS for local HTTPS development supports `REVERB_TLS_CERT` and `REVERB_TLS_KEY`; the optional `REVERB_CA_FILE` lets the broadcaster trust a local CA without disabling certificate verification. The local Laragon environment terminates TLS at its existing HTTPS virtual host and proxies to loopback port 8080. No queue worker is required for these synchronous, after-commit invalidations; broadcaster timeouts are bounded and failures cannot undo persistence.

The private type channel carries only empty invalidation events. Every card and count is fetched again through authorized HTTP services. Updates refresh automatically even with a dialog open, selected cards or additional column pages loaded; the board restores loaded page depth and scroll positions. Dragging and active mutations defer a refresh until safe. Open card details update without replacing unsaved work or comment drafts. Reconnection requests a fresh read. Response generations, configuration/definition versions and view-bound encrypted cursors prevent late responses or another filter/lane's cursor from entering the view. If Reverb is unavailable, a 20-second polling fallback refreshes the board automatically.

The existing workflow header now contains search, filter and grouping controls, compact overview segments, a conditional selection-actions menu and connection indicator next to settings. These controls no longer create separate toolbar, overview, selection or live-update strips. Small screens wrap controls within that same header and open search as an anchored field; the board title and back/settings controls remain available. Grouping opens the shared workflow dialog. Selection actions use an accessible native popover and retain the per-card bulk execution dialog.

The settings dialog keeps its shared shell, fixed footer and independently scrolling body. Its keyboard-accessible tabs separate personal presentation from shared capacities. Card information uses selectable tiles; each capacity row has labeled fields and a responsive layout. Server errors open the relevant tab and focus its invalid field. Existing AJAX persistence, loading states and no-navigation behavior are unchanged.

The live indicator becomes green only after the private subscription succeeds, rather than merely opening the transport. Its focus/hover tooltip distinguishes connecting, authorizing, authorization failure and network failure. Clicking it retries a disconnected connection. Private authorization uses the current CSRF token and JSON transport on every attempt, with bounded timeout and abort on teardown. Failed subscriptions retry after 15 seconds; Pusher handles transport reconnection and online events also reconnect. A successful resubscription invalidates the authorized board view.

### Local Laragon operation

The local setup uses `wss://jobic.test/app/{public-key}` on the same HTTPS origin as the application. Apache proxies `/app/` to the loopback-only Reverb listener at `127.0.0.1:8080`; the broadcaster itself uses internal HTTP. Thus browsers use the site's existing TLS endpoint rather than a separate secure port. Only `proxy`, `proxy_http` and `proxy_wstunnel` modules are needed. The project virtual host is kept as `jobic.test.conf`, following [Laragon's documented custom-vhost convention](https://laragon.org/docs/pretty-urls), so regeneration does not overwrite the proxy.

`tools/development/Start-Reverb.ps1` discovers the active Laragon PHP version and supervises one listener per checkout. A named mutex prevents duplicate supervisors, an existing port owner is never replaced, and an exited Reverb process is retried after five seconds. Output goes to ignored `storage/logs/reverb.out.log` and `reverb.error.log`; startup retries record no environment data. Run it with Windows PowerShell, or add a project-specific `autorun` entry to `C:/laragon/usr/Procfile`, as described in [Laragon process management](https://laragon.org/docs/easy-to-extend). The local Procfile entry is installed and the supervisor is running independently of this shell. Laragon already starts at Windows login. Closing the parent supervisor stops supervision; `artisan reverb:restart` restarts its child while supervision continues. Production should use its process manager and TLS proxy rather than this development script.
# Editorial collaboration

The card detail dialog now includes a discussion. Authors can mention up to five authorized board members using `@[Name](user:ID)`; the server validates each recipient against the content type, current state, and selected board. A comment contains plain text only. Notifications are private, can be switched per kind in the bell dialog, and are removed from the feed whenever the recipient loses card access. The hourly `kanban:send-reminders` task sends a deduplicated warning for upcoming editorial deadlines.

The bottom of the card dialog has separate keyboard-accessible Discussion and Work tabs. Discussion opens first. A control beside the tabs collapses the whole lower workspace to give the embedded content editor more room; choosing either tab expands it again. Work uses two continuous columns for assignment/priority and deadline/dependencies, collapsing to one column on narrow screens. Each tab keeps its own draft and save action. Board navigation and dialog closing proceed immediately when nothing is dirty. Unsaved card content, work or comment drafts use the themed in-page discard dialog; the embedded editor suppresses its own unload prompt and lets the board coordinate the decision and lease release. Browser tab/window closure still uses the browser-owned warning only for actual unsaved card changes.

Changing the grouping choice, including selecting no grouping, now saves the user's board preference immediately through the shared AJAX command. A failure restores the last saved choice. The notification dialog opens on the feed and uses a gear in its header to toggle personal notification switches without adding a persistent section beneath the feed.

An approval-enabled workflow state (`allows_approval`) can request review from one to five authorized members. Requests submit the current immutable revision; all reviewers must approve before the package records final approval, while one rejection returns it for changes. Configure `RequireApprovedRevision` on the relevant transition when that transition must wait for approval. Existing workflow permission and package transition checks remain authoritative for all entry points.

Card work now stores a priority (low, normal, high, urgent). Shared board options store `color_mode`: `none`, `signals`, or `priority`. Signal mode colors overdue deadlines, pending reviews, and high priorities in that order. The workflow report includes each column's oldest card and arrivals and departures during the last 30 days, counted only for cards currently visible in the board's filtered query.

### Extension surface

Trusted extensions may register board, settings, calendar, insight, notification, column, card and detail view slots with `Hooks::addView`; the rendered HTML mounts in the existing Vue workspace. Read endpoints expose a separate scalar `extra` map for the board, card, column, detail, calendar, insights, members and notifications. Extensions cannot replace core fields or widen authorized queries. Notification creation exposes sending/sent actions. See `docs/hooks.md` for exact names, safe contexts, ordering and failure behavior. Custom filter drivers remain the supported way to change board membership and search restrictions; extension data is presentation-only.
