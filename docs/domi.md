# Page presentation with Domi

Jobic requires jobmetric/domi 1.14.1 or later. The published API is Domi::setLocalize(namespace, data); it has no addLocalize method. App\Support\Page::addLocalize is the project's thin adapter to that API.

GET controllers call Page::prepare(pageName) after the locale is known, and Page::addLocalize('feature', [...]) for page-specific public data. The published Domi layout renders its localization registry once, as application/json with JSON_HEX_TAG/AMP/APOS/QUOT escaping. JavaScript reads it via resources/js/common/page.js; do not use eval, raw inline assignments or duplicate data-* JSON payloads. AJAX locale changes replace this registry from the new server presentation. Never serialize a Request, model, env, password, token or secret into it.

Use Domi for PHP-generated page metadata, assets and JS localization. Keep static page structure in shared Blade layouts; no concatenated HTML in controllers. common.base extends domi::layout. The published override at resources/views/vendor/domi/layout.blade.php owns the document and renders Domi links, top/bottom scripts, localization, footer content and modals. common.base maps CMS stacks/sections and hooks into this layout; it must not own a separate document. Maintain documented CMS hooks and normal controller/service boundaries.

All save buttons use loadingButton: preserve nodes/state, disable, display translated loading text and restore on success/failure. Settings remain AJAX; navigation is not a saving indicator. Translation keys live in lang/en and lang/fa and use descriptive names. Browser tests must check pending and restored labels, disabled state and document identity.

The installer registers its JavaScript messages under `installation` through `IntroController::index` and `Page::addLocalize`. `wizard.js` reads them with `pageData`; do not pass translated messages through data attributes. Step/progress templates live in the language catalog, and numbers use the document locale. Server-rendered labels and option descriptions use the same catalog through Blade translations; option values remain stable configuration identifiers. Installation validation attributes use the translated field names.

The installation studio has its own scoped visual design while inheriting the shared Domi document. Language changes use a CSRF-protected JSON request followed by a rendered-page fetch; only the installer and public Domi registry are replaced. The document remains mounted. Unsaved values are copied directly between form controls in memory, never localStorage or sessionStorage, and visible passwords are masked again. The owner may change language at any unfinished step; controls are temporarily locked while a request or installation task sequence is in progress. Reduced-motion preferences disable decorative transitions. The password meter indicates the minimum length, not a security score.

The installer registers `jquery` and `select2` with `Domi::setPlugins` in its GET controller. Preserve that jQuery instance when the application bundle loads. Select2 controls are destroyed before a language refresh and initialized again with the new direction and localized messages. Native select values and input events remain the source for validation and conditional fields. Notifications use `common/toast.js`, shared with the admin shell; field-specific errors remain beside their controls. Password toggles are excluded from Tab order, and task checkmarks animate only when the server reports completion, respecting reduced-motion preferences.

Select2 dropdowns attach to the positioned installer root, outside transformed/animated panels. Connection cards expose idle, pending, success and error states. Database and Redis steps cannot continue without a successful test of their current inputs; changing connection fields immediately resets the client confirmation. Responses to tests started before an edit cannot unlock continuation. Language changes preserve this in-memory state; refreshed pages receive only booleans calculated from server-side fingerprints of persisted values, never credentials or fingerprints themselves. A failed retest removes the previous server confirmation. Connection animations indicate request state, not artificial progress.

Compatibility fixes belong in the package source at `../maral/packages/domi`. Release 1.14.1 includes PackageCore EnumMacros compatibility and explicit nullable string parameters. Jobic installs the published package without vendor patches or Composer repair scripts. Verify package discovery and localization tests on upgrades; see `docs/package-development.md`.


## Domi layout integration

Page::addStyle and Page::addScript delegate to setStyle/setScript. Domi::setTitle and other metadata setters render in the package layout. Common Vite bundles remain in the head stack so Vite can resolve development/production assets. The localization object is also exposed as window.localize for Domi scripts; AJAX language refresh updates both representations without evaluating response scripts.

The published override retains the package output contracts and adds CMS language/direction/body sections, escaped attributes, safe JSON, and correct asset URLs on nested routes. It omits the package's hardcoded search schema and env-based base URL. On Domi upgrades compare the published layout to vendor/jobmetric/domi/resources/views/layout.blade.php and rerun asset-order/localization tests. Public assets are published with artisan vendor:publish --tag=domi-assets.

## Sign-in language

The Vuero login uses the shared `common.language-options` view, `sendSettings`, `refreshPresentation` and toast helper used by admin settings. The guest-only, throttled `login.language` endpoint validates via its Form Request and Authentication service, stores only a session language preference and exposes documented saving/saved hooks. No account preference is changed before authentication. `Page::prepare` and `Page::addLocalize` provide page-scoped translations. Presentation refresh changes copy and direction while preserving the document and draft controls; a visible password is masked again. Existing password recovery pages retain their current locale behavior.

Language CRUD registers `Domi::setPlugins(['jquery', 'datatable'])` on the list only. Pass an array: the published API uses its first argument as the plugin list. Form/list toolbar keys and public labels use Page::addLocalize; the CMS renders them with DOM textContent. Domi currently has no standalone toolbar builder. Each language page has its own Vite entry and only imports shared transport/presentation helpers.

All product selects now use the shared Domi Select2 registration in Page::prepare and common/selects.js; installation keeps its own specialized initializer. The published CMS layout resolves stylesheet URLs through asset() so nested routes never request relative plugin CSS. Table and form toolbar keys still use the Domi localization registry; the installed Domi 1.14 API has no toolbar/button factory, so shared CMS controls consume that registry without adding unrelated APIs to the package. The approved UI refinement uses an Actions dropdown and a split Save button.
